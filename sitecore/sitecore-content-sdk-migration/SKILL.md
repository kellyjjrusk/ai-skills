# Sitecore JSS → Content SDK Migration

JSS 22.x left support in June 2026 and JSS 23.x does not support SitecoreAI at all. Every SitecoreAI / XM Cloud front-end still on JSS is running unsupported code, and new platform features (App Router, React 19, Agentic Studio integration, secure editing hosts) only land in the Content SDK. This skill turns a JSS repo into a Content SDK repo with a plan the team can execute and verify.

## Operating constraint: no CMS access

You cannot log in to SitecoreAI, the Cloud Portal or the Deploy app. Everything you know comes from:
- the repository (the user pastes files, attaches a zip, or the workspace has the repo)
- output the user runs and pastes back (build logs, `npm ls`, browser console, Deploy logs)

So: never claim an environment setting is correct — tell the user exactly where to check it and what value to expect. When you need CMS-side facts (site name, rendering host config, editing secret), ask for them or give the precise click-path.

## Version facts move fast — verify first

Before writing the plan, run a web search for the current Content SDK upgrade guide on doc.sitecore.com (search: `Content SDK upgrade JSS doc.sitecore.com`) and the latest `@sitecore-content-sdk/nextjs` version on npm. Baseline as of late 2026:

| Line | Status | Stack |
|---|---|---|
| JSS 22.x | Out of support (June 2026) | Next 14/15, Pages Router |
| JSS 23.x | XM/XP only — no SitecoreAI | — |
| Content SDK 1.x | Maintenance into early 2027 | Next 15, Pages Router, App Router beta from 1.2 |
| Content SDK 2.x | Active | Next ^16, React ^19, App Router first-class |

Target 2.x unless the user has a hard reason (e.g. a dependency locked to Next 15). Going 1.x first and 2.x later doubles the work.

## Workflow

### 1. Inventory the JSS app

Run the bundled scanner against the repo root:

```bash
python3 scripts/scan_jss_usage.py <repo-root> --out jss-inventory.md
```

It reports: every `@sitecore-jss/*` package and version, every import site grouped by symbol, JSS-only APIs that have no direct Content SDK equivalent (chromes, Experience Editor hooks, `temp/config`, middleware plugins, `componentFactory`), env vars in use, custom plugins under `src/lib/**/plugins`, and the router type. Read its "Risk flags" section first — those decide effort.

If the repo is not available, ask for: `package.json`, the `src/lib` tree listing, `src/middleware.ts`, `next.config.js`, `.env` (redacted), one representative component, and `xmcloud.build.json`.

### 2. Decide the path

- **Fresh scaffold + port (recommended for most):** `npx create-content-sdk-app@latest nextjs` into a sibling folder, then move components, styles, custom pages and custom logic across. Sitecore's own guidance is to sync your app to the template; with 81% fewer starter files, porting into the clean starter is faster and leaves no JSS residue.
- **In-place upgrade:** only when the app has extensive non-Sitecore code entangled with the starter (custom server, heavy middleware). Even then, diff against a fresh scaffold file by file.

State which path and why in one paragraph.

### 3. Produce the migration plan

Write `MIGRATION-PLAN.md` with these sections (use the template in `references/plan-template.md`):

1. Target versions (Content SDK, Next, React, Node)
2. Package swap table (old → new)
3. File-by-file actions (keep / replace from scaffold / port / delete)
4. Component porting checklist (one row per component)
5. Middleware & plugin rewrites
6. Environment variables (old → new, where each is set: local `.env`, Deploy app env vars, Vercel/Netlify)
7. Editing host & Pages builder verification
8. Test plan and rollback

### 4. Execute the mechanical changes

Use `references/api-map.md` for the symbol-by-symbol mapping. Key moves:

- Replace `@sitecore-jss/sitecore-jss-nextjs` with `@sitecore-content-sdk/nextjs` everywhere; same for `-react`, `-cli` → `@sitecore-content-sdk/cli`.
- `temp/config` and `scjssconfig.json` → `sitecore.config.ts` (`defineConfig`) and `sitecore.cli.config.ts`.
- Implicit component factory → explicit component map. The map is generated by the Content SDK CLI; check the scaffold's `package.json` scripts for the exact generate command and wire it into `prebuild`/`predev`.
- Middleware plugin pattern (`src/lib/middleware/plugins/*`) → `defineMiddleware` chain in `middleware.ts` composing the SDK's locale, multisite, redirects and personalize middlewares plus any custom ones.
- GraphQL services built by hand → `SitecoreClient` from `lib/sitecore-client`.
- Debug: `DEBUG=sitecore-jss:*` → `DEBUG=content-sdk:*` (namespaces such as `content-sdk:layout`, `content-sdk:dictionary`).

When the user's preference is complete files, output whole files, never diffs.

### 5. Things that silently break — check every one

- **Experience Editor is gone.** Content SDK supports only the Pages builder via metadata integration. Any chromes-based code (`EditFrame`, `isExperienceEditorActive`, `withPlaceholder` EE hacks) must be removed, and authors told.
- **Content Editor Preview is not supported** after migration. Tell authors before go-live.
- **Component names must match** the rendering item's `componentName` exactly, case-sensitive. A mismatch renders "Unknown component" only in Pages, not in local dev with mock data.
- **Editing secret** must match between the editing host env (`SITECORE_EDITING_SECRET`) and the CM. Mismatch = blank Pages canvas.
- **Secure editing hostnames** (`xmc-*-eh.sitecorecloud.io`) are automatic in Content SDK — remove any allow-list entries hard-coded for the old public pattern.
- **Edge rate limit is 80 req/s.** Large SSG builds need retries configured; Content SDK exposes retry options on the client — set them, don't rely on defaults.
- **Personalization & analytics** move to `@sitecore-content-sdk/personalize`, `/events`, `/analytics-core`. Re-test variant rendering.
- **Mixed literal/variable GraphQL** inputs fail on Edge — custom queries must use variables throughout.

### 6. Verify

Give the user a runnable checklist (they execute, you interpret results):

```bash
npm ci && npm run lint && npm run build     # must pass with zero sitecore-jss references
grep -rn "sitecore-jss" src/ package.json  # must return nothing
DEBUG=content-sdk:* npm run dev            # watch layout/dictionary calls resolve
```

Then in the browser: home page, a deep page, a 404, a personalized page, a multilingual page. Then in SitecoreAI Pages: open three pages, edit a text field, add a component from the toolbox, save, publish to Edge, confirm on the delivery site.

Ask the user to paste failures back. Diagnose from the actual error, not a guess.

## Output

Deliver: `jss-inventory.md` (from the script), `MIGRATION-PLAN.md`, full replacement files for anything you changed, and a short author-impact note (what editors will notice). Keep chat replies short; the plan carries the detail.
